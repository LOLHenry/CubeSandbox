# Android 沙箱渲染：按需高帧率（完整稿）

> 本页提出问题并给出技术诉求。实现仍在验证。按需 / 快速两条并行，分由不同团队承担。

## 标题

Android 沙箱：AI Agent 基础设施之一，诉求按需高帧率渲染

## 1. 背景：训练对沙箱要什么，现在差在哪

### 训练到底要沙箱干什么

Mobile GUI 训练不是「开一台模拟器给人看」，而是用很多台 Android 环境给模型采轨迹：每台循环 **截图 → 决策 → 点击/滑动**，采完一批就更新策略。沙箱要同时满足三件事：

1. **能并开：** 一次训练要同时挂一批环境。公开工作里，学术在线 RL 常见 **几十路**（DigiRL 到 64 路模拟器 / 128 CPU）；桌面 GUI RL 可以到 **256 路**（ARPO）；工业级 GUI RL 是 **数千台 VM、百万级 interactive rollout**（UI-TARS-2）。Android 侧对标工作每台只要 **2 核**（DigiRL、MobileGUI-RL）。
2. **能截图、能操作：** 观测就是屏幕图，动作就是坐标手势。人不需要 60fps 视频流；模型一步看一张图。
3. **采得起、供得上：** 环境路数直接决定 GPU 侧一轮要等多久。ARPO 把并行从 8 提到 256，单 epoch 采样从 **6 小时以上降到约 1.2 小时**。路数开不满，训练墙钟就上去，同样预算少做实验。

单条轨迹并不长：DigiRL 每条最多 **10～20 步**，MobileGUI-RL 最多 **25 步**，评测任务几十到一百条量级。主流范式是 **「中短轨迹 × 多路并行 × 多轮迭代」**，不是「一轮 100 万步、100 路一起跑」。下面不用这个假算例。

### 现在存在的问题（实在讲）

我们这套 Android 沙箱是 MicroVM 里跑 ReDroid，`gpu_mode=guest`，画面走 **CPU 软渲染（SwiftShader）**。catalog 默认 **4 核 / 6GiB、1080×1920**。内部画像：复杂界面软渲染 **CPU 热点超过 50%**，部分场景 **帧率低于 10fps**。

具体就两件事：

- **截图时画得慢：** 模型要的是一张已经画完的图。帧率低于 10fps 时，凑齐这张图要多等。
- **不截图时还在画：** 决策（模型推理）往往占逐步大部分墙钟，此时没人看屏幕，合成仍按「给人看」的方式刷，CPU 继续烧。

对训练的实在后果：同样一批机器，**并开路数上不去**（每路比同行更吃核），采轨迹变慢，一轮实验更贵、更慢。

## 2. CPU 渲染对业务问题的影响（按真实训练规模量化）

### 2.1 主影响：每路更吃核 → 同样集群少开一半量级的环境

| 来源 | 并行规模 | 单环境 CPU | 说明 |
| --- | --- | --- | --- |
| DigiRL（NeurIPS 2024） | 最多 **64** 路 Android 模拟器 / 128 CPU | **2 核** | 1.74 条轨迹/分钟；单机硬堆会掉到 0.74 |
| MobileGUI-RL（2025） | 随 batch 的 AVD 池 | **2 核** / 3GiB | 1080×2400；436 任务 × 每任务 4～8 条 rollout，每条 ≤25 步 |
| ARPO（2025，桌面 GUI） | **256** 路并行环境 | — | 8 路时一轮采样 &gt;6h，256 路约 **1.2h** |
| UI-TARS-2（2025） | **数千** 台 Windows/Ubuntu/Android VM | — | 支撑百万级 interactive rollout |
| 本沙箱 catalog | 取决于节点核数 / 4 | **4 核** / 6GiB | 软渲染热点 &gt;50% |

对标 Android 在线 RL 用 2 核就能开一台；我们因为软渲染占掉约一半 CPU，catalog 按 **4 核** 装箱。同样 64 核节点：对标约 **32 路**，我们约 **16 路**，**并发约为对标的 50%**。

ARPO 已经说明：并行路数差一个数量级，采样墙钟可以从 6 小时掉到 1.2 小时。我们若只能开一半路，就停在这条曲线的慢端。工业级若按数千 VM 计，每台多吃 2 核，就是整集群 **多买近一倍 CPU** 才能维持同样路数。

**业务上就是：** 同样预算少跑一半量级的并行实验，排队更长，一周训完的量更少。这是对「大规模并行训练」的主打击。50% 为内部热点推到装箱核数的量级，最终以节点实开路数校准。

### 2.2 次影响：截图多等 100ms～1s，不是主矛盾

&lt;10fps 时，稳定截图常常多等 **100ms～1s**。主流轨迹只有十几到二十几步，决策本身又是秒级，**单条轨迹多等几秒，对「人能不能用」几乎无感，也撑不起「训练体验差」这个帽子。**

它仍然值得做，原因不是 100ms，而是：复杂页若迟迟画不完，截图窗口会从百毫秒拖成数秒，并行池被慢环境拖尾（ARPO 也写了 GUI 环境延迟会拖所有并行环境）。快速渲染要防的是这条尾，不是日常那 100ms。

## 3. 技术诉求：库瓶颈 / 业务逻辑 → 两条手段

不先拆清「谁在慢、谁在空转」，按需和快速会对不准团队。

**基础库瓶颈（画一帧太贵）→ 快速渲染**

- SwiftShader 把 Setup、光栅化、PixelRoutine、纹理采样、混合全放在 CPU 上，1080p 复杂页热点多在像素/纹理循环，且未按鲲鹏 **SVE/SVE2** 把热算子向量化。
- Skia / HWUI 的 DisplayList 回放、`saveLayer`/模糊、RenderThread 同步，把过量绘制灌进 SwiftShader。
- Reactor JIT 抬高首帧。

**业务逻辑问题（不该画的时候还在画）→ 按需渲染**

- 按给人看的 vsync 持续合成，决策期无截图仍在刷。
- 默认全屏 1080×1920、动画未关、无脏区整帧重画。
- 截图整帧读回，和「只要一张稳定图」不匹配。

由此只收两条手段（并行、分团队）：

1. **按需渲染：** 非截图阶段减少无效渲染，把空转那一半核让出来，把可并开路数抬到接近 2 核装箱的量级。  
2. **快速渲染：** 做 SwiftShader 热路径 **算子改造**（鲲鹏 SVE/SVE2 向量化 + 多线程），缩短出帧，截图期尽快拿到稳定帧。

## 依据（脚注，不入口号正文）

- DigiRL, NeurIPS 2024：64 路 / 128 CPU，约 2 核一台；1.74 traj/min；单任务 10～20 步。  
- MobileGUI-RL, 2025：AVD **2 核**；436 任务，7B 每任务 8 条 rollout，每条 ≤25 步。  
- ARPO, 2025：256 路并行；8 路 epoch 采样 &gt;6h，256 路约 1.2h。  
- UI-TARS-2, 2025：数千 VM（含 Android），百万级 interactive rollout。  
- 本沙箱：4 核 / 6GiB，`gpu_mode=guest`；内部画像 CPU 热点 &gt;50%、部分场景 &lt;10fps。
