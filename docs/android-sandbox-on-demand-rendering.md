# Android 沙箱渲染：按需高帧率（材料稿）

> 本稿只覆盖渲染，不含快速启动。供评审后改写入正式材料。

## 标题

Android 沙箱：AI Agent 基础设施之一，诉求按需高帧率渲染

## 场景诉求

**按需高帧率渲染：** Mobile GUI Agent 训练需大量沙箱并发，软件渲染 CPU 占用过半；截图时部分场景帧率偏低。

## 业务问题

**1. 按需**

- Agent 闭环是「截图 → 决策 → 交互」，只有截图时需要屏幕画面。
- 决策阶段以模型推理为主（公开评测中可占逐步时延七成以上），此时持续刷帧没有观测收益，却占用沙箱 CPU。
- 结果：无效合成挤占算力，单机可并发沙箱变少。

**2. 流畅**

- 截图时需要尽快得到稳定可用的画面。
- 复杂界面下软件渲染 CPU 占用可超过 50%，部分场景帧率低于 10fps；出帧慢则单步环境等待变长。
- 渲染持续占 CPU，进一步压低单机并发。

**数字口径**

| 数字 | 含义 | 不是 |
| --- | --- | --- |
| CPU 占用 >50%、部分场景 <10fps | 沙箱侧软件渲染画像（内部实测） | 端到端训练时间里「渲染等待」的占比 |
| 决策约占逐步时延七成以上 | 模型规划/反思为主，Agent 并不按 60fps 看屏 | 渲染优化能按同比例缩短训练墙钟 |

## 技术诉求

**按需高帧率渲染**

**1. 按需：** 降低非截图阶段的渲染占用，提升单机并发。控制手段必须先验证，不能写进方案定案：

- 「截图时再合成」可能更慢：合成往往在截图前已完成，截图触发等于把本可提前完成的工作推后。
- 「决策间隙降频」依赖能判断间隙：决策在 Agent 侧，沙箱默认看不到「正在推理」。
- 降频可能拖慢稳定：后续帧依赖前面的合成结果，降频后到达稳定画面的时间可能变长，与「截图要快」冲突。

按需是否成立，取决于能否证明：减少非观测期合成后，CPU 明显下降，且「动作 → 稳定截图」不明显变长。

**2. 流畅：** 同等部署密度下，缩短截图路径上的软渲染出帧时间（多线程光栅化、算子与合成优化）。
